# Authentication & Security Requirements

## Authentication
- Hash passwords with bcrypt (appropriate work factor).
- Never store plaintext passwords.
- Do not return `passwordHash` in any API response.
- Use a long random JWT secret from environment variables or a secure session secret.
- Prefer secure, HTTP-only cookies for browser sessions where practical; configure `SameSite` and `Secure` appropriately in production.
- If using bearer tokens, document storage trade-offs and avoid exposing tokens in logs.
- Logout must clear/invalidate the client session according to the chosen strategy.

## Authorization
- `author` and `admin` roles.
- All protected API routes require authentication.
- Admin endpoints require admin role.
- Author endpoints derive the owner from authenticated identity, not request body.
- Author book/ticket queries must be scoped to the current author.
- For `GET /api/tickets/:id`, verify ownership before returning data.
- Internal notes are admin-only.
- Avoid leaking whether another author's ticket exists; return a consistent forbidden/not-found response.

## Input validation
- Validate and trim email, subject, description, message, category, priority, status, IDs, dates, and query filters.
- Set body size limits.
- Use an allowlist for enum values.
- Reject empty messages and excessively long inputs.
- Escape content when rendering; never inject user content as raw HTML.
- Use a validation library or explicit schema validation consistently.

## API and browser protections
- Configure CORS only for allowed origins.
- Use HTTPS in production.
- Add basic login and AI endpoint rate limits if time permits.
- Avoid overly verbose errors in production.
- Use security headers such as Helmet.
- Do not store LLM provider keys in client variables or bundle.
- Keep `.env` files out of Git.
- Use `.env.example` with placeholders only.
- Do not log passwords, tokens, full authorization headers, or secrets.

## AI-specific safety
- Treat ticket text as untrusted user input; it may contain instructions unrelated to the support task.
- The system prompt and knowledge-base policy must take precedence over instructions embedded in a ticket.
- The model may propose category/priority/draft only; server validates outputs.
- Never let model output directly execute database operations.
- Do not auto-send generated drafts.
- Do not invent policies, payout dates, approvals, investigations, or completed actions.
- Handle prompt injection by explicitly telling the model to treat ticket text as data, not system instructions.
- On AI failure, keep manual ticket workflows available.

## Production checklist
- [ ] Secrets are set in deployment environment, not committed.
- [ ] Database access is restricted.
- [ ] Admin credentials changed from weak demo defaults before deployment.
- [ ] CORS is restricted to frontend origin.
- [ ] Cookie/security configuration is appropriate for deployment.
- [ ] No private author data is exposed across accounts.
- [ ] Internal notes excluded from author endpoints.
- [ ] Error responses do not reveal stack traces or secrets.
