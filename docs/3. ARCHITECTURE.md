# Architecture

## Recommended stack
- Frontend: React + Vite + JavaScript
- Styling: plain CSS (fastest to maintain for this deadline)
- Backend: Node.js + Express
- Database: MongoDB Atlas (Mongoose) or local MongoDB for development
- Authentication: bcrypt password hashing + JWT in an HTTP-only cookie where feasible; if bearer tokens are used, keep handling deliberate and documented
- AI: server-side LLM provider adapter (OpenAI or Groq; configurable)
- Live updates: client polling every 5–10 seconds
- Deployment: frontend on Vercel; API on Render or equivalent

Do not treat this stack as mandated by BookLeaf; it is the proposed implementation for a short deadline.

## Logical architecture
1. React client
   - Auth state and route guards
   - Author screens
   - Admin screens
   - API client
   - Polling for ticket changes
2. Express REST API
   - Authentication middleware
   - Role/ownership authorization
   - Validation and error middleware
   - Route handlers/controllers
   - Services for ticket workflows and AI
3. Database
   - Users/authors
   - Books
   - Tickets
   - Ticket messages/replies and internal notes (can be embedded in ticket for MVP)
4. LLM provider
   - Called only from backend
   - Uses compact prompt context and knowledge-base text
   - JSON output validated before persistence
   - Graceful fallback when unavailable

## Request flow: create ticket
1. Author submits form.
2. Client sends `POST /api/tickets`.
3. Authentication middleware identifies user.
4. Validation checks subject, description, and book ownership.
5. Ticket is saved with `Open` status before optional AI work can block the request.
6. AI service classifies/prioritizes ticket with timeout.
7. If AI succeeds, persist suggestions; if it fails, preserve ticket and mark AI analysis unavailable.
8. Return created ticket.
9. Author ticket list receives update on next poll.

## Request flow: send response
1. Admin opens ticket.
2. Client requests ticket detail and message history.
3. Admin requests AI draft or edits an existing draft.
4. Backend sends a compact, grounded prompt to configured LLM.
5. Draft is returned for human review; it is not automatically sent.
6. Admin submits response.
7. Backend verifies admin role, persists a public reply, and optionally changes status.
8. Author client receives the response through polling.

## Error handling
- Central Express error handler with `{ error: { code, message, details? } }`.
- Use 400 for invalid input, 401 for unauthenticated, 403 for unauthorized, 404 for missing records, 409 for conflicts, 429 for rate limiting, and 500 for unexpected errors.
- Do not return stack traces in production.
- AI errors should not stop ticket creation or manual response workflows.
- Add request timeout to AI calls and reasonable request body size limits.

## Cost and reliability
- Send only the current ticket text, relevant book fields, and concise knowledge-base facts.
- Do not send all tickets or the entire database to the model.
- Use a small/low-cost model that is available to the account.
- Do not call AI on every page load; call it on ticket creation and explicit draft generation.
- Cache the generated draft only as ticket data if helpful; do not repeatedly regenerate without an action.
- Clearly indicate AI-generated content and require admin approval before sending.

## Deployment architecture
- Client uses `VITE_API_BASE_URL`.
- Server uses `PORT`, database URI, JWT secret, and LLM API key from environment variables.
- Configure CORS for the deployed frontend origin.
- Use HTTPS deployment URLs.
- Seed demo data using a one-time seed command, not on every server startup.
